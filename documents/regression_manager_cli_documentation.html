Regression Manager

Command-line reference for a fictional Java-based regression test runner. This document defines an example command syntax for prototyping a documentation-grounded CLI assistant. These flags are invented for this sample and are not a reference for any real product.

1. Overview

Regression Manager is a fictional Java command-line application that launches regression test suites, selects environments and test groups, controls parallel execution, reruns failed tests, and writes reports.

Purpose of this document: provide a realistic, internally consistent example of CLI documentation for developing an LLM agent. The command names, flags, defaults, and behaviors below are sample conventions only.

Typical tasks

  • Run a complete regression suite or a selected test group.
  • Choose a configuration properties file and target environment.
  • Run tests in parallel with a specified number of workers.
  • Rerun failed tests after the first execution.
  • Set the application version/build label and output directory.
  • Generate HTML, JUnit XML, or both report formats.
  • Preview the effective settings or print the tool version without running tests.

2. Requirements and assumptions

  • Java 17 or later is assumed for this fictional tool.
  • The application JAR is named regression-manager.jar.
  • Commands are shown for a POSIX-style shell. Windows PowerShell and Command Prompt have different quoting and line-continuation rules.
  • Paths may be absolute or relative to the current working directory.
java -version
java -jar regression-manager.jar --help
java -jar regression-manager.jar --version

The help and version flags are designed to work without the normal test-run arguments.

3. Command syntax

java -jar regression-manager.jar
  --suite <suite-name>
  --config <path>
  [--env <environment>]
  [--tests <selector>]
  [--version-label <label>]
  [--parallel]
  [--threads <count>]
  [--rerun-failed]
  [--rerun-count <count>]
  [--rerun-only]
  [--results-dir <path>]
  [--report <html|junit|all>]
  [--tag <tag>]
  [--timeout-seconds <seconds>]
  [--dry-run]
  [--verbose]

Angle-bracket values are placeholders and must be replaced. Square brackets indicate optional arguments. Do not type the brackets themselves.

Command structure

  1. java starts the Java runtime.
  2. -jar regression-manager.jar identifies the executable JAR.
  3. Arguments after the JAR are interpreted by Regression Manager.
Important: the literal argument --version prints the Regression Manager software version. The separate --version-label argument labels a test run, such as build-2026.10.20.

4. Required arguments

ArgumentValueDescriptionExample
--suite<suite-name>Required for test runs. Name of the registered suite to execute. Allowed sample values: smoke, regression, full.--suite regression
--config<path>Required for test runs. Properties file containing application URL, credentials references, timeouts, and other environment settings.--config ./config/qa.properties

Both required arguments are mandatory for a normal test execution. They are not required when using the standalone --help or --version action.

6. Feature recipes

Basic regression run

java -jar regression-manager.jar \
  --suite regression \
  --config ./config/qa.properties

Runs the named suite using the settings in the specified properties file.

Parallel execution

java -jar regression-manager.jar \
  --suite regression \
  --config ./config/qa.properties \
  --parallel \
  --threads 6

Runs the suite with six workers. The thread count is valid only with --parallel.

Rerun failures

java -jar regression-manager.jar \
  --suite regression \
  --config ./config/qa.properties \
  --rerun-failed \
  --rerun-count 2

Performs the initial run and allows up to two additional attempts for each failed test.

Rerun a previous run's failures

java -jar regression-manager.jar \
  --suite regression \
  --config ./config/qa.properties \
  --rerun-only \
  --previous-run RM-20261020-001

Runs only tests marked failed in the referenced earlier run. It does not run the full suite first.

Set build version and reports

java -jar regression-manager.jar \
  --suite full \
  --config ./config/staging.properties \
  --version-label release-4.8.1 \
  --report all \
  --results-dir ./artifacts/release-4.8.1

Labels the run and writes both report formats under the selected output directory.

Preview without running tests

java -jar regression-manager.jar \
  --suite regression \
  --config ./config/qa.properties \
  --parallel \
  --threads 4 \
  --dry-run

Checks the proposed arguments and displays the planned run without starting test execution.

7. Complete examples

Example A — Select tests by ID

java -jar regression-manager.jar --suite regression --config "./config/qa.properties" --tests "PAY-101,PAY-102" --report all

Example B — Tagged tests with a run label

java -jar regression-manager.jar --suite smoke --config "./config/staging.properties" --tag critical --version-label "build-2026.10.20" --results-dir "./results/build-2026.10.20"

Example C — Parallel run with retry and verbose logging

java -jar regression-manager.jar --suite regression --config "./config/qa.properties" --parallel --threads 8 --rerun-failed --rerun-count 3 --report all --verbose

Example D — Check the application version

java -jar regression-manager.jar --version

Example E — Validate a command before execution

java -jar regression-manager.jar --suite regression --config "./config/qa.properties" --parallel --threads 4 --dry-run
When displaying commands in a chat interface, preserve quoting around paths or values that may contain spaces. Prefer rendering a shell-safe command string from an argument list rather than concatenating untrusted text into a shell command.

8. Validation and compatibility rules

  1. For normal test execution, both --suite and --config are required.
  2. --help and --version are standalone actions and cannot be combined with test-run arguments.
  3. --threads requires --parallel; accepted values are integers from 1 through 32.
  4. --rerun-count requires --rerun-failed; accepted values are integers from 1 through 5.
  5. --rerun-only requires --previous-run.
  6. --rerun-only cannot be combined with --rerun-failed in the same invocation.
  7. --tests and --tag are mutually exclusive.
  8. --report must be one of html, junit, or all.
  9. --timeout-seconds must be a positive integer.
  10. Paths must exist where required: the JAR and configuration file must be readable. The results directory must be writable or creatable.
  11. Unknown flags should cause a validation error rather than being silently ignored.

Agent behavior when information is missing

If a request says “rerun failed tests” but does not say whether to retry failures from a new run or rerun a previous run, ask a clarifying question. If the user asks for parallel execution but omits the worker count, use the documented default only if the agent is configured to apply documented defaults; otherwise ask.

9. Exit codes

CodeMeaningSuggested handling
0Command completed successfully and all selected tests passed, or a standalone informational action succeeded.Read the generated report for details.
1One or more tests failed.Review failed test details; rerun if appropriate.
2Invalid arguments or incompatible options.Correct the command using the usage text.
3Configuration file missing or invalid.Check the config path and required properties.
4Execution timed out.Inspect logs and consider whether a longer timeout is appropriate.
5Unexpected internal error.Save verbose logs and investigate the underlying failure.

Exit codes are proposed conventions for this sample tool, not codes from an actual executable.

10. Notes for building a CLI-generation agent

  1. Use this HTML as a knowledge source. Parse headings, tables, lists, and code examples; preserve the association between each flag and its constraints.
  2. Retrieve relevant sections. For a request about retries, provide the agent with the rerun option descriptions, examples, and validation rules rather than the entire document if the context window is limited.
  3. Extract intent into structured fields. For example: suite, config path, parallel flag, worker count, retry mode, retry count, version label, and report format.
  4. Validate deterministically in code. Check required arguments, value ranges, mutually exclusive options, and dependencies after the LLM returns structured data.
  5. Build the command from an argument list. Use a defined flag map rather than asking the LLM to invent command syntax. Quote the displayed command for the target shell.
  6. Ask follow-up questions when needed. Do not guess a suite, config file, previous run ID, or unsupported feature.
  7. Separate generation from execution. Display the command first. If execution is added later, require an explicit user action and use safe process invocation with argument arrays, not shell concatenation.
  8. Test the agent with examples. Include valid requests, missing required arguments, unknown flags, conflicting flags, invalid counts, paths with spaces, and follow-up changes to prior requests.
Suggested first milestone: the agent accepts a chat request, returns a structured intent object, validates it against these rules, and displays the exact command plus a short explanation. It does not execute the Java process.
